# Stripe Connect signup flow

`POST /api/register` only emails an OTP. `POST /api/verify-otp` takes the normal registration fields; `return_url` and `refresh_url` are optional, but must be provided together if the mobile app has its own HTTPS callbacks. Otherwise the API uses its own `/stripe/onboarding/return` and `/stripe/onboarding/refresh` routes under `STRIPE_ONBOARDING_BASE_URL` (defaults to `APP_URL`). After validating the OTP, the API creates the local user and a Stripe Accounts v2 merchant-configured connected account with Express Dashboard access under the platform's `STRIPE_SECRET`, then saves the returned ID in `users.stripe_account_id`. The verification response includes the ID in `data.user.stripe_account_id`, a Sanctum token in `data.token`, and a single-use onboarding link in `data.onboarding_url` with `data.onboarding_link_expires_at`. This currently applies to both `client` and `freelancer` registrations. The account requests `card_payments` for a later direct-charge integration; no payment is created at registration.

The connected account cannot receive payments just because it was created. The signed-in user must complete Stripe-hosted onboarding:

1. Open the signup response's `data.onboarding_url` in a browser, not an embedded mobile WebView. If it is null, expired, or already used, call authenticated `POST /api/stripe/onboarding-link` to get a fresh `data.url`. The API keeps the completed signup if initial link creation fails.
2. The default backend refresh route shows a page asking the user to return to the app and request a new link. It does not create another link in an unauthenticated browser session. The mobile app should call the authenticated link endpoint again and open the new URL. If the app supplies its own `refresh_url`, its handler can perform that step directly.
3. The default backend return route asks the user to return to the app. When the app resumes, it should call `GET /api/stripe/account-status` with the bearer token. A return from Stripe does not prove onboarding is complete. Check `data.ready_for_payments` and `data.onboarding_required`; show another onboarding action while current or eventual requirements remain. Stripe can also be reviewing an account that has no outstanding onboarding fields. The `details_submitted` response field is derived from whether v2 reports due requirements, rather than a native v2 field.

Both callback URLs must be HTTP(S) URLs. Stripe test mode accepts HTTP for local testing; live mode requires HTTPS. Set `STRIPE_ONBOARDING_BASE_URL` to the public API base URL (including a deployment path such as `/bezzie`); `http://localhost` will not work from a mobile device. The local AMPPS value is `http://localhost/bezzie`. The API hosts the default callback pages. Never expose `STRIPE_SECRET` in the client app or put the bearer token in a callback URL. Do not store onboarding URLs in the database: they expire and are single-use. Store the connected account ID and query `GET /api/stripe/account-status` for current activation state.

This implements account creation and onboarding only. Charging a client for a job and collecting the platform commission are separate payment-flow work.
