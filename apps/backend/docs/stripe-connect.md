# Stripe Connect signup flow

`POST /api/register` only emails an OTP. `POST /api/verify-otp` takes the normal registration fields; `return_url` and `refresh_url` are optional, but must be provided together if the mobile app has its own HTTPS callbacks. Otherwise the API uses its own `/stripe/onboarding/return` and `/stripe/onboarding/refresh` routes under `STRIPE_ONBOARDING_BASE_URL` (defaults to `APP_URL`). After validating the OTP, the API creates the local user and a Stripe Express connected account through Accounts v2 under the platform's `STRIPE_SECRET`, then saves the returned ID in `users.stripe_account_id`. The verification response includes the ID in `data.user.stripe_account_id`, a Sanctum token in `data.token`, and a single-use hosted Account Link in `data.onboarding_url` with `data.onboarding_link_expires_at`. The account requests merchant `card_payments` and recipient `stripe_balance.stripe_transfers`; no payment is created at registration.

The connected account cannot receive payments just because it was created. The signed-in user must complete Stripe-hosted onboarding:

1. Open the signup response's `data.onboarding_url` in a browser, not an embedded mobile WebView. If it is null, expired, or already used, call authenticated `POST /api/stripe/onboarding-link` to get a fresh `data.url`. The API keeps the completed signup if initial link creation fails.
2. The default backend refresh route shows a page asking the user to return to the app and request a new link. It does not create another link in an unauthenticated browser session. The mobile app should call the authenticated link endpoint again and open the new URL. If the app supplies its own `refresh_url`, its handler can perform that step directly.
3. The default backend return route asks the user to return to the app. When the app resumes, it should call `GET /api/stripe/account-status` with the bearer token. A return from Stripe does not prove onboarding is complete. Check `data.ready_for_payments` and `data.onboarding_required`; show another onboarding action while current or eventual requirements remain. Stripe can also be reviewing an account that has no outstanding onboarding fields. The status endpoint uses the v1-compatible Account representation exposed for the Accounts v2 connected account.

Both callback URLs must be HTTP(S) URLs. Stripe test mode accepts HTTP for local testing; live mode requires HTTPS. Set `STRIPE_ONBOARDING_BASE_URL` to the public API base URL (including a deployment path such as `/bezzie`); `http://localhost` will not work from a mobile device. The local AMPPS value is `http://localhost/bezzie`. The API hosts the default callback pages. Never expose `STRIPE_SECRET` in the client app or put the bearer token in a callback URL. Do not store onboarding URLs in the database: they expire and are single-use. Store the connected account ID and query `GET /api/stripe/account-status` for current activation state.

## Provider payouts

New Express accounts use a manual payout schedule so providers can withdraw their available balance from the mobile wallet. Existing accounts are switched to manual scheduling when their first in-app payout is submitted.

The provider wallet reads `GET /api/freelancer/payouts`. The response separates the app `wallet` ledger from Stripe `balance`: successful provider earnings immediately credit `wallet.available`; Stripe funds can still be pending settlement. Payment records are the credit ledger and withdrawal requests are the reservation/debit ledger. Amounts are summed in integer minor units per provider and currency. Repeated payment webhooks cannot duplicate a credit.

`POST /api/freelancer/payouts` accepts an amount and a client-generated idempotency key. It locks the provider row, checks the wallet's unreserved balance, and creates one withdrawal entry. The requested amount immediately leaves the available wallet balance and appears in `wallet.reserved`. The minimum is `STRIPE_MINIMUM_PAYOUT_MINOR` (default `1000`, AUD 10.00). Different concurrent requests cannot reserve more than the available wallet balance.

If Stripe funds are unsettled, the request has status `awaiting_settlement`. `php artisan wallet:process-withdrawals` submits it once the connected account has sufficient settled funds. Configure Laravel's scheduler to run every minute (`* * * * * cd /absolute/backend/path && /path/to/php artisan schedule:run >> /dev/null 2>&1`). Wallet loading is not required for the background processing. A Stripe payout can then be pending, in transit, paid, failed, or canceled. Paid withdrawals remain deducted; confirmed failures/cancellations release the reservation automatically. A network timeout keeps funds reserved and retries the same Stripe idempotency key. Uncertain submissions older than 23 hours require reconciliation instead of being blindly submitted again.

Providers manage their bank account through `POST /api/freelancer/payouts/dashboard-link`. New and existing withdrawing providers use manual Stripe payouts. Historical automatic payouts are reconciled, including all Stripe result pages, and deducted from the ledger so they cannot be withdrawn again.

Configure the Connect webhook endpoint for `payout.created`, `payout.updated`, `payout.paid`, `payout.failed`, and `payout.canceled` at `/api/stripe/webhook`. The scheduled processor also reconciles payout status if a webhook was missed. Test-mode payouts do not move real money. Platform-only test payments can credit the wallet ledger without funding the connected Stripe account; those withdrawals remain pending until the account is funded.

### End-to-end payment and withdrawal testing

Keep `STRIPE_TEST_PLATFORM_PAYMENTS=false` for both Stripe test and live payment/payout flows. This is now the default. The `true` override is only for onboarding-independent QA; it records earnings without crediting a provider Stripe balance. On an existing deployment, explicitly change this value in the server environment and run `php artisan config:cache`; changing the repository default does not override an existing environment value.

The wallet displays total earnings, the available app wallet balance, reserved withdrawals, paid withdrawals, and Stripe pending settlement separately. `GET /api/freelancer/payouts` includes `payment_mode.test_mode` and `payment_mode.platform_test_payments` so the app can explain test-mode limitations. A successful payment row alone does not establish that funds are available to withdraw.

Existing platform-only test charges do not move to a provider when this setting changes. Reconcile the historical PaymentIntents, destination accounts, refunds, and prior transfers in Stripe before arranging any corrective transfer. The wallet ledger credits recorded successful earnings, but a bank payout must never bypass Stripe's available funds check or charge the customer again. New tests should use a fresh job and the direct provider payment flow. Test-mode withdrawals do not pay a real bank account.

### Deploying the wallet reservation update

Back up the backend and database, deploy all files in the matching wallet-ledger package, then run `php artisan migrate --force`, `php artisan optimize:clear`, and `php artisan config:cache`. The migration adds the Stripe submission timestamp and attempt sequence to withdrawal requests. Keep existing `.env`, keys, uploads, and database. Enable the scheduler before accepting withdrawal requests; otherwise reservations will wait until the command is run manually. Deploy the backend before releasing the updated provider app. The app falls back to the previous settled-balance behavior when the server does not return `wallet`.

Before live rollout, reconcile historical successful payments (especially platform-only test charges), bank payouts and refunds. Historical test ledger earnings are not real bank funds. Never mix test and live histories/accounts without an explicit reconciliation. Use a fresh sandbox account for acceptance tests: successful payment -> immediate wallet credit -> withdrawal reserves funds -> settlement -> one Stripe payout -> paid. Also test insufficient wallet funds, request replay, failed payout restoration and missed webhook reconciliation.

### Wallet screen status refresh

The wallet refreshes when the screen opens and when the user pulls to refresh. There is no periodic polling or app-resume refresh. Servers advertise `wallet_sync_supported` in the payout dashboard; updated apps then call authenticated `POST /api/freelancer/payouts/sync` (30 requests/minute). This reconciles the signed-in provider's existing payouts, processes only their reserved pending withdrawals, and returns newly retrieved Stripe balances. Older servers retain read-only wallet behavior until this update is deployed. The scheduler remains necessary when the app is closed. Stripe pending funds are never reduced artificially and withdrawals are never marked paid without Stripe confirmation.
